# 西门子 · 稳定连接：工业协议与边缘网关

> 技术栈：MindConnect Nano / IoT2040 / Lib / Software Agent + OPC UA / S7 / Modbus（以西门子 MindSphere 为案例）
> 适用场景：工业协议如何终结、边缘网关与断网续传怎么落地

连接是工业 IoT 的第一公里。消费 IoT 可以设备直连云，工业里这几乎不成立：老设备不联网、协议不统一、车间还可能断网。在 MindSphere 里，这层叫 MindConnect——它既是协议翻译官，又是断网时的缓冲垫。

在工厂网络里，"能 ping 通云"和"能稳定上送数据"是两回事。DMZ 默认不允许控制器出网，防火墙只允许由内向外的单向 TLS 隧道。边缘网关在本地做协议终结、数据聚合、断网续传，把"不确定性"挡在车间内，只把干净数据交给云端。

## 1.问题背景：现场协议如何被 MindConnect 终结 / 转换

工业现场的真实状况是。

### 1.1 现场协议的七重现实

- **协议碎片化且根深蒂固**：Modbus RTU 跑串口，OPC UA 走安全会话，S7 是西门子母语，Profinet 跑工业以太网。给老设备装新协议栈既不经济也不可行。
- **网络并不总在线**：车间到云专线会抖动，直连云让断连时数据直接丢失。
- **安全边界**：IT/OT 间有明确网络边界，不能云端直连控制器。
- **时间不同步**：多设备各自计时，振动、温度时间戳错乱，做关联分析失真。
- **存量设备无网口**：大量 S7-300、老 DCS 连以太网都没有。
- **安全分区（DMZ）**：IEC 62443 要求分区隔离，控制器不能暴露给 IT。
- **协议要向前兼容**：新设备用 OPC UA，老设备用 Modbus，十年后还得一起跑。

这些现实决定了：协议转换、续传、计算、同步放在 MindConnect 上，比甩给云端更合理。

### 1.2 为什么不能直接上云

| 原因 | 后果 | MindConnect 的应对 |
|------|------|------------------|
| 证书与防火墙 | S7 不具备 TLS 能力，密钥烧进 PLC 风险高 | 证书与隧道终结在网关 |
| 带宽与成本 | 1kHz 振动全量上云浪费带宽 | 边缘聚合 RMS，带宽降一个数量级 |
| 语义缺失 | 裸地址 "DB4.DBW10=235" 无人能懂 | Aspect 映射翻译为"主轴轴承温度=52.3℃" |
| 时间基准 | 多设备各自计时，毫秒级抖动无法对齐 | NTP/PTP 统一对时 |

## 2.设计理念：为什么用 MindConnect 家族，而不是让设备直连云

MindConnect 不是一个单一硬件，而是一组面向不同现场形态的连接方案，其共同价值是把"现场的乱"收敛成"上行的稳"。

### 2.1 MindConnect 家族：按现场形态分四种

| MindConnect 形态 | 适合场景 |
|------|------------|
| MindConnect Nano | 工业边缘硬件网关，连已有 PLC/控制器，内置安全，棕地安装即用 |
| MindConnect IoT2040 | 基于 SIMATIC IOT2000 的入门级网关，适合较小数据量的生产环境 |
| MindConnect Lib | C/C++ 库，嵌入设备固件，让设备原生具备上送能力 |
| MindConnect Software Agent | 跑在 Windows/Linux 上，连接既有数据源（如数据库、SCADA） |

它们北向统一对接 Ingestion Service，南向通过 OPC UA、S7、Modbus TCP 等对接现场。关键取舍：**实时控制回路留在 OT 内闭环，MindConnect 只承担监控、采集、聚合**。

| 形态 | 适用场景 | 代价 |
|------|---------|------|
| Nano | 棕地产线，高可靠性要求 | 单价高于软件方案 |
| IoT2040 | 数据量小、试点场景 | 缓冲容量有限 |
| Lib | OEM 出厂即带云连接 | 需设备侧二次开发 |
| Software Agent | 已有 SCADA/历史库，不想动硬件 | 依赖主机稳定性 |

为帮助理解"为什么需要这么多种形态"，把常见现场协议的差异列一张表。

### 2.2 现场协议差异与边缘终结方式

| 协议 | 传输 | 安全 | 典型场景 | MindConnect 如何处理 |
|------|------|------|----------|----------------------|
| Modbus RTU | 串口主从轮询 | 无 | 老仪表、变频器 | 经串口读保持寄存器，映射到 Aspect |
| Modbus TCP | 以太网主从 | 无 | 第三方设备 | TCP 读，归一为变量流 |
| S7 | ISO-TSAP 会话 | 弱 | 西门子 PLC | 读数据块/寄存器，只读不写 |
| OPC UA | 发布/订阅 | 证书会话 | 跨厂商、跨系统 | 安全订阅，天然带语义 |
| Profinet | 实时以太网帧 | 分区 | 西门子自动化设备 | 由 PLC/控制器侧经 S7 间接取 |

### 2.3 只读不写与边缘聚合的收益

核心原则：**南向协议只读不写**，把云端误操作风险降到最低。边缘聚合的量化收益：

| 指标 | 全量直连 | 边缘聚合后 |
|------|---------|----------|
| 上送点数 | 1kHz 振动 = 1000/s | 10s RMS = 0.1/s（降约10000倍） |
| 带宽 | 全量原始波形 | 仅上送摘要，按需回传波形 |
| 防火墙 | 多端口、多方向 | 单一 443 端口 TLS 隧道 |

## 3.实际应用：MindConnect 承接第一公里

### 3.1 边缘接入架构：协议归一上行

下面这张图展示协议如何在 MindConnect 处被终结并归一上行：左侧是带各自协议标签的现场设备（Modbus、S7、OPC UA、私有协议），中间是 MindConnect 家族（Nano / IoT2040 / Lib / Software Agent）完成协议转换、断网续传、本地预处理与建立安全隧道，右侧 MindSphere 云端通过 Ingestion Service 拿到统一接入、经 Time Series Service 落库。

![MindConnect 边缘接入](/images/series/iot-platform-design/siemens/02-siemens-industrial-edge.svg)

![MindConnect Software Agent 管理界面（来源 documentation.mindsphere.io 官方截图）](/images/series/iot-platform-design/siemens/ms-mindconnect-agent-ui.png)

![MindConnect Nano 边缘网关硬件（来源 Siemens 官方产品图）](/images/series/iot-platform-design/siemens/ms-mindconnect-nano-hw.png)

落地时常见的做法是：MindConnect Nano 以 DIN 导轨壁挂安装于控制柜，通过 S7/OPC UA/Modbus 读取 PLC 与仪表数据，在本地做预处理与聚合，按周期（如 Nano 每 10 秒一个传输周期）经加密隧道上送 Ingestion Service；断网期间数据写入本地缓冲区，恢复后按序补传；Software Agent 则适合已有 SCADA/历史数据库的场景，把既有数据源"翻译"成 MindSphere 能理解的变量流，无需改动现场设备。

### 3.2 落地样例：灌装线 MindConnect Nano

食品厂 12 台灌装机，控制器型号不一。每台机柜装一台 Nano，S7 读 PLC、Modbus TCP 读称重仪表。Aspect 映射把裸地址翻译为带语义的变量：

```yaml
mindconnect:
  agent: mindconnect-nano
  transport_period: 10               # 每 10 秒一个传输周期
  protocols:
    - type: S7
      endpoint: tcp://plc-filler:102 # 只读
    - type: modbus-tcp
      endpoint: tcp://scale-meter:502
  mappings:
    - source: "DB5.DBW2"
      variable: "pressure"           # 灌装压力
      unit: "bar"
    - source: "holding_register:40001"
      variable: "weight_deviation"   # 称重偏差
      unit: "g"
  upstream:
    endpoint: "https://gateway.<tenant>.mindsphere.io"
    buffer_on_disconnect: true       # 断网缓冲，恢复后补传
```

每周计划内断网维护期间，Nano 把快照写入本地缓冲，恢复后按时间戳补传，Time Series 曲线连续无空洞。

**工程经验**：传输周期按物理量选（温度 10-30s，振动 RMS 1-10s），缓冲容量按"最长断网时长 × 采集频率"反算，Aspect 映射集中管理——12 台机共用一份变量字典，保证"灌装压力"同名同单位。

### 3.3 选型决策链

```
设备有网口 + 长期可靠 → Nano
预算紧 + 数据量小 + 先验证 → IoT2040
OEM 新产品 + 能改固件 → Lib
已有 SCADA/历史库 + 不想动硬件 → Software Agent
```

远程诊断靠 Nano 心跳上报，Fleet Manager 发现离线即派单。建议定期做断网演练：拔链路数小时验证缓冲不溢出、恢复后无空洞。

## 4.注意事项


- **网关本身是单点**：MindConnect 一旦故障，整片区域数据就断了。关键产线建议同柜双 Nano 热备，Fleet Manager 监控心跳。
- **协议转换不是万能钥匙**：毫秒级安全回路必须留在 OT 内闭环。落地时把"哪些变量可以上云"列成白名单，安全相关位（急停、联锁）一律不映射。
- **时间同步精度要匹配场景**：亚毫秒联动用 PTP，秒级监控用 NTP。在 Asset 元数据中记录时间来源，便于下游判断可信度。


## 5.小结

工业的稳定连接靠的不是"设备直连云"，而是 MindConnect 在协议、续传、计算、同步上的兜底。它把碎片化的现场协议归一为 MindSphere 的统一接入，在网络中断时保住数据，在实时与带宽之间找到平衡。MindConnect 家族（Nano / IoT2040 / Lib / Software Agent）覆盖从硬件网关到固件库到软件代理的全谱系，但共同守一条铁律：只读不写、实时闭环留在 OT。正是这种"边缘兜底"，让海量时序数据能顺畅进入 Ingestion / Time Series——这是（三）的前提。

| 维度 | 直连云 / 通用网关思路 | MindConnect 工业思路 |
|------|--------------|--------------|
| 协议 | 各设备直连或单一 MQTT 网关 | 边缘终结多协议，归一为 Aspect 变量流 |
| 断网 | 数据直接丢失 | 本地缓冲，恢复后按序补传 |
| 安全 | 明文或密钥烧进 PLC | 网关终结证书，只读不写 |
| 带宽 | 全量原始上送 | 边缘聚合（RMS 等），降 1~2 个数量级 |
| 选型 | 一刀切 | Nano / IoT2040 / Lib / Software Agent 按场景分 |

一句话收尾：工业稳定连接的本质是"边缘兜底"——MindConnect 把协议、续传、计算、同步挡在车间内，只把干净数据交给云端，这既是海量时序能顺畅进入 Ingestion / Time Series 的前提，也是后面各篇的底座。
