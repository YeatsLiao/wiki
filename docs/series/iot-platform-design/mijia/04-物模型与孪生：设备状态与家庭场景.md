# 小米米家 · 物模型与孪生：设备状态与家庭场景

> 技术栈：MIoT-Spec 物模型（属性 / 事件 / 服务）+ 家庭 / 房间 / 场景（以小米米家 / MiOT 为案例）
> 适用场景：用统一物模型描述设备、组织家庭场景


米家设备连上了、消息也会流了，但米家 App 怎么知道「灯现在是开着还是关着」？用户说「打开客厅灯」，系统怎么知道客厅灯是哪一台？这一篇以小米 IoT（MiOT）平台为案例，讲消费级 IoT 如何用 **MIoT-Spec（小米 IoT 设备协议规范，即物模型）** 把千奇百怪的硬件抽象成统一数据，用设备状态同步（影子）记住最新状态，再用「家庭/房间/场景」的层级把设备组织成人能理解的空间。物模型是消费级 IoT 能不能「规模化」的关键。米家接入了上千款不同厂商的设备，如果每款都要 App 单独写一套 UI 与解析逻辑，接入成本会指数爆炸。MIoT-Spec 用一套标准「词汇表」描述任意设备，让 App 能自动生成面板、让小爱能自动语控、让规则引擎能自动编排——硬件差异被吞进模型里。如果说（二）解决了「进得来」、（三）解决了「流得动」，那本篇解决的就是「看得懂」：让平台真正理解每台设备能做什么、现在是什么样。

这套能力在米家内部是「设备能被平台读懂」的前提，没有它，后面的自动化、语音、运营都无从谈起。尤其当家设备品类上千、固件版本上百时，只有统一模型能让新设备「即插即懂」，不必为每个新品单独适配前端。

## 1.问题背景：米家设备状态与场景组织的真实痛点

### 1.1 硬件语义各异

不同厂商的「开关」可能是 bool、可能是 0/1/2 三档、可能是字符串。米家 App 不可能为每款设备写一套 UI——所以小米定义了 MIoT-Spec 标准规范，统一接入产品的控制指令。例如 A 厂插座用 `switch: 0/1`，B 厂用 `power: off/on`，C 厂甚至用 `state: "close"/"open"`，没有统一模型，App 解析会乱套。

### 1.2 状态随时在变、且会失联

灯开着时被拔掉电源，小米云若只信实时上报，状态就卡在「开」；用户手机也想知道「它到底现在什么样」，需要一份保真镜像。设备掉电、断网、重启都会让实时状态失真，影子状态（最后已知）才是用户能信任的真相源。否则会出现「云端显示灯开着、实际已断电」的尴尬，联动判断也会跟着错。

### 1.3 用户按空间思考，不按设备思考

人说的是「客厅」「卧室」「回家模式」，不是「设备 did 为 xxxx 的继电器」。米家 App 的家庭/房间体系正是为这种思维方式而生。一个用户家里可能有二十多台设备，靠「客厅灯 1、客厅灯 2」命名远不如「客厅 → 主灯/氛围灯」直观。

### 1.4 语音/自然语言要能映射到动作

「我回家了」应翻译成一组设备动作，需要把自然语言锚定到具体的物模型字段，小爱同学才能正确执行。若设备没有规范物模型，小爱连「客厅灯」对应哪个 property 都不知道，语音控制就会失效。物模型因此也是语音与自动化能「零代码」生效的基础设施。

### 1.5 模型要能被机器与人共用

物模型不只是给 App 渲染面板用的，它还是规则引擎、小爱、运营看板共同的数据契约。一旦模型定义清晰，自动化、语音、批量运营都能直接复用，不用为每类消费者重写适配。这也是为什么米家坚持「先定模型、再写固件」的接入顺序，模型先行能把后期返工降到最低。

## 2.设计理念：为什么米家用 MIoT-Spec + 状态同步 + 层级抽象

三件事各有分工，叠起来才完整：从「数据」到「状态」到「空间」，构成米家能理解万物的基础。

### 2.1 MIoT-Spec：设备的统一词汇表

小米用「属性（可读写状态）/ 事件（上报）/ 服务（下行指令）」三类来描述任意设备（在代码侧对应 Service 包含 property / action）。灯有 `power` 属性、门锁有锁定服务、传感器有温度事件。平台与 App 只看模型，不看芯片；类型以 `urn:miot-spec-v2:device:...` 的 type 标识。例如一盏米家智能灯的 type 可能是 `urn:miot-spec-v2:device:light:...`，其下挂一个 Light 服务，服务里有 `on`（bool 属性）与 `brightness`（0~100 整数属性）。

这种三级结构（设备 → 服务 → 属性/事件/服务）让任意新品都能被「套模板」描述，而不必发明新协议。

### 2.2 设备状态同步：云端保真镜像

小米云为每台设备维护 `reported`（设备实际状态）与 `desired`（期望状态）。设备离线时，App 读影子就能知道「最后已知状态」；下行指令写进 `desired`，设备上线即对齐。它本质是（三）里离线消息的结构化版。当用户在 App 点「开灯」而设备离线，`desired.power=on` 被记录，设备上线后自动执行，用户感知不到中间断网。

### 2.3 家庭/房间/设备：人能理解的组织层

在物模型之上再建「家庭 → 房间 → 设备」「场景 = 一组动作」的层级，让联动与语音有空间坐标；米家 App 的账号与家庭体系即承载此模型。一个「家庭」下可有多个「房间」，每个房间挂若干设备；「回家模式」场景则是一组跨设备的动作编排。层级还支持「家庭共享」——主人把家庭分享给家人，多人共管同一批设备，权限与归属清晰。

### 2.4 自然语言锚定到模型

小爱同学把「打开客厅灯」解析成「家庭 X.客厅.灯.power = on」，靠的就是 MIoT-Spec 物模型 + 家庭层级这两张地图。小爱先定位「客厅」房间下的「灯」设备，再对该设备的 `power` 属性写 `on`，整个过程依赖模型与层级两张索引。没有物模型，语音就只能靠关键词硬匹配，无法泛化到「把卧室调成阅读模式」这类组合指令。一句话：**MIoT-Spec 解决「怎么描述设备」，状态同步解决「记住最新状态」，层级解决「按人的方式组织」**。三者缺一则联动写死、语音失灵、状态失真。

## 3.实际应用：MIoT-Spec、状态同步与家庭场景

### 3.1 MIoT-Spec 物模型定义

每台设备创建产品时绑定一个功能定义（标准功能模板），属性（如亮度 0~100）、事件（如有人移动）、服务（如校准）被规范描述；平台据此自动生成面板与小爱语控、快捷卡片所需的字段。开发者在「定义产品功能」时须遵循模板，否则自定义功能无法被小爱控制。一个典型属性定义包含：`siid`（服务实例 id）、`piid`（属性实例 id）、`type`（数据类型）、`format`（取值格式）、`access`（可读/可写/可通知）、`value-range`（取值范围）与 `unit`（单位）。例如亮度属性可定义为 `{siid:2, piid:2, type:"uint8", format:"brightness", access:["read","write","notify"], value-range:[0,100,1], unit:"percentage"}`；事件则描述触发条件与负载字段，服务描述可下发的动作与入参。

```json
// MIoT-Spec 物模型片段（公开规范，代表性示例：米家智能灯）

{

  "type": "urn:miot-spec-v2:device:light:0000A001:xiaomi.mijia:v1",

  "services": [

    {

      "siid": 2,                                          // 服务实例 ID

      "type": "urn:miot-spec-v2:service:light:00007801",

      "properties": [

        { "piid": 1, "type": "bool",  "format": "on",         "access": ["read","write","notify"] }, // 开关

        { "piid": 2, "type": "uint8", "format": "brightness",  "access": ["read","write","notify"], "value-range": [0,100,1], "unit": "percentage" } // 亮度

      ],

      "events": [

        { "eiid": 1, "type": "urn:miot-spec-v2:event:low-battery" } // 低电量事件

      ]

    }

  ]

}
```

### 3.2 设备状态同步保状态

设备定时上报 `reported`；米家 App 下发指令写 `desired`。弱网/离线时，这份同步状态就是双方唯一真相源，避免「云端以为开、实际已关」。当设备重新连上，先把 `reported` 与 `desired` 做对账：若 `desired` 有未执行项，下发执行；若 `reported` 与 `desired` 长期分叉，触发注意事项里的告警。影子让「控制」与「状态」分离：用户点开关写的是期望，设备回报的是实际，二者最终收敛。

### 3.3 家庭/房间/场景与小爱联动

设备挂到房间下、房间挂到家庭下；「回家模式」场景把「开门 + 开灯 + 关窗帘 + 开空调」编排成一组动作，用户一键触发或经小爱/规则引擎触发。层级还让权限可控：家庭成员可按房间授权，比如只让保姆控制「门口」设备而不碰「卧室」。场景作为「动作组」与物模型解耦存储，换设备时只需重新绑定，场景逻辑不变。小爱同学借助 MIoT-Spec 与层级，把「打开客厅灯」映射到具体设备的属性写操作；大模型加持的超级小爱还能听懂复杂指令、支持语音创建自动化，无需用户记设备 did。例如「把卧室空调调到睡眠模式」会被解析为「卧室.空调.mode = sleep」，再经物模型写操作下发。语音创建自动化时，小爱会把口语转成一条标准规则（见（三）），存进同一套规则引擎，与手动创建的规则等价。

### 3.4 模型版本与兼容

MIoT-Spec 支持以 type 版本号管理演进，新品类加新服务、老设备保持旧模型，平台按版本协商字段。这让生态能在不破坏存量设备的前提下持续扩展能力，是「碎片化」长期可控的关键。

## 4.注意事项

- （1）**物模型要预留扩展，但别过度设计**：枚举/范围/单位（如亮度格式、单位）从一开始就定清楚，否则旧设备新 App 会解析错；但也别为「也许用得上」的字段堆模型，增加端侧负担。

MIoT-Spec 还要求勿随意修改模板中属性的格式/单位/范围。一旦某属性 `value-range` 或 `unit` 被已发货设备采用，后端修改会导致新旧设备行为不一致，必须靠版本兼容而非破坏性变更。新增能力应走「新增服务/属性」而非「改旧字段」，保证老设备不被新模型拖垮。

- （2）**状态同步要防「期望」与「实际」长期分叉**：若设备始终无法对齐 `desired`（如坏了），应超时告警并回写，避免影子永远停在「指令已发」的假象，误导用户与联动判断。

例如 `desired.power=on` 但设备一周未上报 `reported.power=on`，应标记设备异常并提示用户检查，而不是继续把它当「已开」。联动引擎在读取状态时应优先用 `reported`，避免基于过期 `desired` 做二次触发。

- （3）**层级迁移要处理设备归属**：设备换房间、家庭转让、租客退租时，物模型与状态要随之迁移/解绑，否则会出现「别人家的灯出现在我家」；米家 App 的家庭分享与转让即为此设计。

转让家庭时，原主人的设备绑定、场景、权限应整体移交，并吊销旧账号的访问令牌（呼应（二）一机一密解绑）。设备换房间时，其参与的场景引用也要同步更新，否则会出现「回家人还在开旧房间灯」的幽灵联动。

## 5.小结

MIoT-Spec 把异构硬件翻译成统一数据，设备状态同步在弱网下守住「最新状态」这个真相，家庭/房间/场景层级让人用空间而非设备 did 去思考，小爱同学则借这两张地图把自然语言落到具体动作。至此，单一米家设备的「状态与语义」已经齐活：它能被描述、被追踪、被组织、被语音操控。下一章进入「海量设备如何被批量运营」——物模型定义了「每台设备是什么」，而 OTA 与运营解决的是「数亿台设备怎么一起被养好」。

| 维度 | 工业/通用 IoT 思路 | 米家/MiOT 消费级思路 |
|------|----------------|------------------|
| 设备描述 | 各家私有协议 / 定制 UI | MIoT-Spec 统一词汇表（属性/事件/服务） |
| 状态 | 实时上报为准 | 影子 reported/desired 保真镜像 |
| 组织 | 按设备 ID | 家庭 → 房间 → 设备、场景 = 动作组 |
| 语音 | 关键词硬匹配 | 自然语言锚定物模型字段 |
| 演进 | 破坏性升级 | type 版本号协商、向后兼容 |

一句话收尾：MIoT-Spec 把异构硬件翻译成统一数据，设备状态同步在弱网下守住「最新状态」这个真相，家庭/房间/场景层级让人用空间而非设备 did 去思考——物模型，是消费级 IoT 能「规模化」的真正底座。
