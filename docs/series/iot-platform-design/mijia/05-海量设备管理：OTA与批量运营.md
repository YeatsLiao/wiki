# 小米米家 · 海量设备管理：OTA与批量运营

> 技术栈：小米统一 OTA（差分 / 灰度 / 回滚）+ 批量指令与运营指标（以小米米家 / MiOT 为案例）
> 适用场景：亿级设备的固件升级与批量运营怎么做

## 0. OTA 不是锦上添花，是生死线

米家设备卖出去只是开始。固件有 bug 要修、功能要迭代、活动要批量下发——这些事不可能靠用户一个个手动升级。这一篇以小米 IoT（MiOT）平台为案例，讲海量米家设备怎么被「批量运营」：统一 OTA 如何用差分 + 灰度 + 回滚把风险压到最低，以及运营侧要用哪些指标盯住整片设备海。对消费级 IoT 来说，OTA 不是「锦上添花」，而是「生死线」。一台工业网关可以派人现场刷机，一台米家灯泡只能靠用户无感地自己升级。海量设备一旦因一次坏升级集体变砖，召回成本与口碑损失都是灾难级的。所以米家的 OTA 设计，核心不是「快」，而是「可控、可观测、可退」。

本篇顺着（四）的物模型往下，看平台如何把「养设备」变成一套有节奏、有闸口、有眼睛的运营系统。

## 1. 问题背景：米家海量设备运营的真实痛点

### 1.1 设备散落在千万个家庭

你没法派人人上门刷机，所有升级必须「设备自己完成、用户无感」。米家靠小米 IoT 平台的统一 OTA 把这件事平台化。一个版本发布往往要触达从第一代到最新代、横跨十几种芯片的同一产品线，平台必须按机型分组推送，而不是一刀切。

### 1.2 固件包大、带宽贵

完整固件几 MB，对电池/弱网设备是灾难；全量推送还会瞬间打爆 CDN 与设备。平台侧倾向差分包以减小流量。以 2MB 全量包为例，若用差分可压到几十到几百 KB，对百万级设备就是节省数 TB 的下载量与数倍的升级时长。

### 1.3 一次坏升级等于集体变砖

升级失败变砖、或新固件引入死循环，会引爆海量客诉与退货。米家因此强制固件签名 + 灰度 + 回滚。历史上 IoT 行业多次出现「一夜之间百万设备变砖」的事故，根因都是缺少签名校验或灰度闸口。

### 1.4 你不知道设备「活得好不好」

激活了多少、现在多少在线、升级成功了几成，这些指标不透明，问题就闷在用户家里。小米 IoT 平台提供多维度数据看板（如 7 种数据看板）做运营眼睛。运营每天盯的是「在线率」「升级成功率」「各版本分布」三张图，任何一张异动都要能立刻定位到机型与版本。

### 1.5 运营动作要批量、要可撤销

临时改配置、发公告、拉黑某批问题设备，必须是批量且能回滚的。例如发现某批次传感器上报异常，运营要能一键隔离该批次并下发修正配置，事后还要能撤销。若动作不可撤销，一次误下发就会瞬间影响百万设备，没有退路。

## 2. 设计理念：为什么米家 OTA 必须签名 + 差分 + 灰度 + 回滚

核心是把「批量升级」从「赌一把」变成「可观测、可控、可退」，五道防线叠起来才敢按下「升级」键。

### 2.1 固件签名：装得对的底线

米家 OTA 要求上传固件后必须申请签名（否则 OTA 会失败），并配置「支持签名和 HTTPS 的最低版本」，确保只有经平台签名的合法固件能装进设备，呼应（六）的安全启动。签名基于小米 PKI，私钥不出密钥管理服务，设备端用预置公钥验签，验不过直接拒绝安装。这把「谁能给设备装软件」的权限收口到平台，杜绝第三方恶意固件。

### 2.2 差分升级：发得动的省流

平台支持差分包，只下发新旧固件的差异，设备本地合成完整包。包体可大幅缩小，对弱网/电池设备至关重要。差分通常基于二进制比对（类 bsdiff 思路），对代码段变更敏感、对资源段也能增量，合成在设备的空闲内存完成，合成完再整体校验。

### 2.3 灰度、回滚与指标：放得稳、回得去

升级先放测试/小流量（开启测试给内测用户），监控崩溃率/失败率，没问题再分批放量到全量；版本关系还受约束（待升级版本 > 当前 ≥ 最低版本），异常可暂停。灰度维度可以按 did 尾号、地域、机型、用户分组切，逐步从「内部」到「百分之一」到「全量」。版本号单调递增约束还能杜绝「野版本」回退导致的功能错乱。设备保留上一版固件，升级校验失败（签名不对、合成损坏、启动不了）自动回滚到旧版，保证「最坏情况也只是没升级」，并向云端上报失败原因。设备多采用 A/B 双分区或双 bank 机制：新固件写入备用区，启动成功才切换，启动失败自动回退原区。这把「升级失败的代价」从「变砖」压到「没升级」，用户几乎无感。

激活率、在线率、升级成功率、各版本分布，是米家运营日常盯盘的核心；异常版本一眼可见。当某版本升级成功率跌破阈值，看板会标红，运营立刻介入。指标还反向指导灰度节奏：成功率稳才放量，异常即熔断。

### 2.4 批量指令可逆

配置下发、分组指令、问题设备隔离，都走任务模型，可查询、可暂停、可撤销。任务有状态机（草稿/测试中/进行中/暂停/完成/回滚），每一步都可审计。可逆性让运营敢于对海量设备做动作，因为「出错了能退」。一句话：**签名解决「装得对」，差分解決「发得动」，灰度解决「放得稳」，回滚解决「回得去」，指标解决「看得见」**。

## 3. 实际应用：米家统一 OTA 与批量运营

把「升级 + 运营」落到小米 IoT（MiOT）平台一套机制，典型形态如下：

![米家OTA与批量运营](/images/series/iot-platform-design/mijia/05-mijia-consumer-ota.svg)

### 3.1 云端制作差分包与签名

新版本在云端算出差异包，配合版本管理与强制签名，下发为一条 OTA 任务；开发者须先「开启测试」验证再申请上线。云端按在网主流版本维护若干基线，为每个基线生成对应差分包，设备根据自身当前版本拉取匹配的差分，避免「一个全量包喂所有人」。签名在包生成后由密钥服务完成，设备端启动前校验，整条链路上私钥不触达开发者。

### 3.2 灰度分批推送

任务按测试 → 分批 → 全量渐进放量，每阶段校验升级成功率与崩溃率，异常即暂停；版本号须严格满足递增约束，杜绝「野版本」。例如先放内部员工 1%，观察 24 小时成功率与崩溃率，再放 5%、20%，最后全量；任一阵列指标越界即熔断。灰度还能按机型分批，先放风险低的常电设备，再放电池/弱网设备。

```json
// OTA 灰度发布配置（代表性结构，非真实控制台 payload）

{

  "ota_task": {

    "base_versions": ["1.0.0", "1.1.0"],  // 差分基线：按主流在网版本维护

    "strategy": {

      "stages": [                          // 渐进放量批次

        { "phase": "internal", "ratio": 0.01 }, // 内部员工 1%

        { "phase": "canary",  "ratio": 0.05 }, // 金丝雀 5%

        { "phase": "full",    "ratio": 1.00 }  // 全量

      ],

      "auto_rollback": {                   // 自动熔断阈值

        "fail_rate_max": 0.005,            // 失败率超 0.5% 即暂停

        "crash_rate_max": 0.003

      }

    }

  }

}
```

### 3.3 设备端静默升级与回滚

设备下载差分包、本地合成、校验签名后静默安装；睡眠设备利用唤醒窗口完成，用户无感。电池设备会选在电量充足且处在校准的维护窗口（如凌晨）执行，避免升级中途没电变砖；常电设备则在空闲时段后台完成。升级成功后设备上报新版本号，云端据此更新「各版本分布」看板。校验/启动失败回退旧版，并向小米云上报失败原因，归入「升级失败」指标，便于归因。设备上报的失败原因字段（如「签名校验失败」「合成空间不足」「启动超时」）直接进看板，运营据此判断是包问题还是设备问题。回滚本身不计入「成功」，但计入「安全」，因为它避免了变砖。

### 3.4 运营大盘与批量动作

运营侧看激活率/在线率/升级成功率（数据看板）；对问题批次批量下发配置或隔离指令，全部走可查可撤的任务。运营还能对特定机型批量下发参数（如传感器上报周期调优），任务执行进度实时可见，出错可一键回滚到上一配置。数据看板的「7 种」维度（激活、在线、升级、版本、地域、机型、异常）让运营既能看全局又能下钻到单批。

## 4. 注意事项

- （1）**差分基线要选得巧**：基线太老会让差分包接近全量；应按主流在网版本维护少数基线，平衡包大小与合成复杂度，也避免老设备合成负担过重。

维护过多基线会增加云端存储与生成成本，过少则老版本用户拿到接近全量的包，需要按「在网版本分布」动态取舍。建议基线随大版本收敛，让 80% 在网设备都能命中小差分。

- （2）**灰度不是「发了就行」，要设自动熔断**：必须定义明确的失败率阈值（如崩溃率超阈值自动暂停），否则灰度只是走过场；米家的「开启测试 → 分批 → 全量」本身就是一道人工+系统双重闸。

熔断阈值要结合设备量级：百万级设备下，千分之一的失败率也意味着上千台异常，阈值要随规模收紧。熔断后应先归因再放量，而不是简单「重试」，否则会把同一错误推给更多设备。

- （3）**回滚后要追溯根因**：回滚只是止血，必须收集失败设备日志归因（存储不足？签名错？版本关系错乱？），否则同一批会在下次升级再翻车；同时核对「支持签名和 HTTPS 的最低版本」配置。

常见根因是设备剩余空间不足以容纳合成后的完整包，需要在固件规划阶段就预留足够 scratch 区。归因结论应回流到「版本基线选择」与「差分策略」，让下一次升级更稳。

## 5. 小结

海量米家设备的「活着」不等于「运营得好」。固件签名把底线兜住、差分升级把带宽压下来、灰度把风险控下来、回滚把底线兜回、运营指标把全局看住，再加上可撤销的批量指令，才能对数亿台散落设备做持续、低风险的运营。OTA 的本质是「给已经飞出去的飞机换引擎」——必须在飞行中、对用户无感、且随时能退回原状。下一章收尾：这些设备的安全、隐私与高可用怎么保障，把前面五篇收成一条完整的生命周期。

| 维度 | 工业/通用 IoT 思路 | 米家/MiOT 消费级思路 |
|------|----------------|------------------|
| 升级 | 派人现场刷机 | 统一 OTA 静默升级、用户无感 |
| 安全 | 可选签名 | 强制固件签名 + PKI 验签 |
| 带宽 | 全量推送 | 差分包、按基线下发 |
| 风险 | 一刀切放量 | 灰度 + 自动熔断 + 失败回滚 |
| 运营 | 人工巡检 | 数据看板 + 可撤销批量任务 |

一句话收尾：固件签名兜住底线、差分升级压住带宽、灰度与回滚控住风险、运营指标看住全局——OTA 的本质是「给已经飞出去的飞机换引擎」：飞行中、用户无感、随时能退回原状。
