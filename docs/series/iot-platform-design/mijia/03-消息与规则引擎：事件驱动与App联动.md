# 小米米家 · 消息与规则引擎：事件驱动与App联动

> 技术栈：小米云事件路由 + 规则引擎 + 小爱同学（以小米米家 / MiOT 为案例）
> 适用场景：设备事件如何驱动 App 联动与场景


米家设备连上网只是开始。真正让消费级 IoT「有灵魂」的，是「开门了灯就亮、温度高了空调就降」这种联动。

这一类需求本质是一个事件流：设备产生事件 → 小米云判断规则 → 推给米家 App 或其他设备。这一篇讲消息怎么流、规则引擎/场景联动怎么编排、设备离线时消息怎么办，最后落到小爱同学如何用自然语言触发这一切。

事件驱动是消费级 IoT 的心脏。用户的诉求不是「看一个设备状态」，而是「让一堆设备按我的生活节奏协同」。工业里由 SCADA 脚本写死；消费级里，必须由用户自助定义，甚至说一句「我睡了」就生效。这要求消息系统既要扛住十亿级设备的事件洪流，又要让规则对普通用户可读、可改、可撤销。

## 1.问题背景：米家事件驱动与联动的真实痛点

### 1.1 触发链长且跨端

一个「开门」事件，既要推给米家 App 通知主人，又要下发给灯去开，还可能写日志、联动摄像头。单点对单点的硬编码很快变成意大利面，米家平台必须用统一事件通道承载。例如米家智能门锁开门后，理想链路是：门锁上报开门事件 → 玄关灯开 → 窗帘关 → 摄像头进入在家布防 → App 推送「门已开」。这一串动作涉及四类设备与一个 App，必须靠事件总线而非点对点调用。

### 1.2 用户要的是「如果…就…」

场景联动（回家模式、睡眠模式、观影模式）是米家高频需求，必须由用户或平台用规则表达，而不是写死在固件里——小爱同学还支持「语音创建自动化」。用户在米家 App 里拖拽就能建成一条「如果 晚上 10 点 且 人在家 就 关灯」的规则，无需任何编程。规则的热更新能力意味着平台改策略不必重发固件，这是消费级快速迭代的前提。

### 1.3 网络随时会断

设备休眠或掉线时，米家 App 下发「开灯」指令若直接丢弃，用户会觉得「设备坏了」；局域网本地联动可兜底，但跨端远程指令必须可靠。门锁离线时若漏掉「反锁」指令，会成为安全隐患；温湿度传感器离线则只是少一条数据，两类消息可靠性要求不同。所以消息系统必须区分「可丢」与「必达」，不能一刀切。

### 1.4 消息不能丢也不能炸

门锁「已上锁」这种事件丢了有安全隐患；但摄像头秒级视频流若全走同一条规则，会冲垮轻量通道。米家按消息类型分级处理。控制指令、告警事件走高可靠通道，遥测心跳走轻量通道，音视频流走独立媒体通道，三条通道在资源上相互隔离。

### 1.5 语音要能映射到动作

用户说「我回家了」，小爱同学应翻译成一组设备动作，需要把自然语言锚定到具体的物模型字段（见（四））。「我回家了」可能等价于「执行 回家模式 场景」，也可能等价于「打开 客厅灯 + 关闭 摄像头隐私遮蔽」，语义解析依赖物模型与小爱意图库。若设备没有规范物模型，小爱连「客厅灯」对应哪个 property 都不知道，语音控制就会失效。

## 2.设计理念：为什么米家用事件总线 + 规则引擎 + 小爱解耦

关键设计是把「谁产生的事件」「事件该去哪」「谁来触发」三者解耦，让每一侧都能独立演进。

### 2.1 设备只发事件，不关心谁收

米家设备把状态/事件发布到小米云消息通道，带上 did 与时间戳；至于消息被谁消费，设备不知道也不该知道。这是典型的生产者-消费者解耦。设备固件里只需调用「上报属性」或「上报事件」接口，后续谁订阅、做什么，完全由云端规则决定，设备因此能跨品类复用同一套上报逻辑。

### 2.2 规则引擎编排「如果…就…」

小米云用规则把事件翻译成动作——例如规则「开门 → 开灯」命中后，同时做三件事：给米家 App 推通知、向灯下发开灯指令、写一条日志。规则可热更新，不必改设备固件；「回家模式」本质就是一组编排好的动作。规则以声明式表达，平台负责调度与去重，设备无感。

### 2.3 QoS 分级与离线兜底

不同消息选不同可靠性：心跳用最多一次，门锁状态用至少一次，必要场景才用恰好一次。高优消息（告警、控制）优先落盘与重试，低优消息（心跳、统计）允许丢弃。MQTT QoS 0/1 映射到「最多一次 / 至少一次」。

设备不在线时，小米云把下行指令缓存到设备影子（见第四篇），待设备上线立即补发。影子里的 `desired`（期望）与 `reported`（实际）对账，是弱网下状态不失控的关键。断网时本地联动完全不依赖云端。

### 2.4 小爱同学做自然语言入口

语音经「自然语言 → 意图 → 场景/设备控制」的链路，把口语化表达映射到具体物模型字段，端到端触发联动。小爱把「打开客厅灯」解析为「device=客厅灯, property=power, value=on」，与规则引擎共用同一套动作出口。这样语音、App 手动、规则自动三种触发方式，最终都汇到同一个「执行动作」的出口，避免多套逻辑分叉。一句话：**事件总线负责「流动」，规则引擎负责「编排」，QoS/离线负责「可靠」，小爱负责「入口」**。四者各司其职，让「一个事件、多处响应」既不丢也不乱。

## 3.实际应用：米家设备事件 → 小米云 → 多端联动

把上面拆成一条可落地的链路，典型形态如下：

![米家事件驱动与App联动](/images/series/iot-platform-design/mijia/03-mijia-consumer-event.svg)

### 3.1 设备事件上行

门锁「开门」、传感器触发、状态变化，经小米云消息通道上行，带上 did 与设备身份；遵循 MIoT-Spec 的事件定义（见（四））。以米家门窗传感器为例，它上报的是一个 `event` 类型消息，标识「打开/关闭」与发生时间，平台据此触发后续动作。上行消息按类型打 tag：属性上报、事件上报、告警上报走不同 topic，便于规则引擎按订阅路由。

```text
// 小米云设备事件上行 topic 模板（代表性写法，非真实内部路径）

miot/<did>/event       // 事件上报主题，<did> 为设备唯一 ID

miot/<did>/property    // 属性上报主题

miot/<did>/service     // 服务（下行指令）主题
```

```json
// 门窗传感器开门事件消息（代表性 payload，按 MIoT-Spec 事件定义）

{

  "did": "1234567890",

  "type": "event",

  "event": "open",         // 事件类型：开门

  "timestamp": 1763558400, // 事件发生时间

  "msg_id": "evt-0001"     // 消息去重用 ID

}
```

### 3.2 规则引擎编排与 App 推送

小米云订阅这些事件，按规则匹配。「开门 → 开灯」命中后，同时给 App 推通知、向灯设备下发指令、写一条日志。「回家模式」则一次性触发多个设备动作。

一条规则可表达为：`if 门锁.event==开门 then [灯.power=on, App.notify("欢迎回家")]`，条件可叠加「时间窗」「人在家」等上下文。

推送通道对 Android/iOS 分别走系统推送服务。关键事件（门锁异常）走高优先级通知，普通状态变化仅更新 App 内设备卡片，避免通知轰炸。

### 3.3 跨设备联动与本地兜底

开灯指令经同一消息总线下行到灯，实现「一处触发、多处响应」；同一局域网内优先走本地联动，断网仍可用。本地联动由家庭网关或手机在局域网内直接下发，云端只是「同步与远程」的补充。当云端不可达时，本地联动仍能完成「开门开灯」这类核心体验，用户体验不降级。

### 3.4 小爱语音触发与 QoS/离线兜底

用户说「打开客厅灯」「我回家了」，小爱同学解析意图后映射到具体设备的物模型写操作，与规则引擎共用同一套动作出口。复杂指令如「把卧室调成睡眠模式」会被拆成「关主灯、关窗帘、空调调至 26 度」一组动作。

超级小爱（大模型加持）还能听懂更口语化的表达，支持「语音创建自动化」——用户说一句即可生成一条规则。

关键事件用至少一次保证送达。设备休眠时下行指令进离线队列，上线即补发。平台对离线队列设 TTL 与上限，避免堆积——例如门锁离线期间缓存了「反锁」指令，上线后补发一次即可，不能因重传导致反复反锁。

## 4.注意事项

- （1）**规则要避免「环」与「风暴」**：规则 A 触发 B、B 又触发 A 会形成死循环；米家联动链要有防抖与去重，否则一次开门可能打爆全家设备，本地联动也要设执行频次上限。

例如「开门 → 开灯 → 亮度变化事件 → 触发另一规则 → 又开门」这类环，需要在引擎层做执行链追踪与熔断。还应给单条规则的执行加频控（如 1 分钟内同一动作最多触发 N 次），防止抖动引发雪崩。

- （2）**QoS 不是越高越好**：恰好一次开销大，对心跳、温湿度这类可丢失数据用最多/至少一次即可，省电省带宽；只对锁、燃气阀等强一致场景上高可靠。

盲目上「恰好一次」会让轻量设备忙于确认与重传，反而拖垮实时性。经验上，控制类与告警类用「至少一次 + 幂等去重」，遥测类用「最多一次」，就能覆盖绝大多数场景。

- （3）**离线消息要设有效期与上限**：无限堆积会撑爆小米云、也会在设备上线时瞬间灌爆；应设 TTL 与队列上限，过期丢弃并记一笔即可；本地联动与云端补发要协调，避免同一动作重复执行。

设备上线后应先拉影子 `desired` 对齐，再消费离线队列，二者用同一套幂等标识去重。对电池设备尤其要克制：离线指令太多会逼它频繁唤醒，反而更耗电。

## 5.小结

米家消费级 IoT 的「智能感」来自事件驱动：设备只管发事件，小米云规则引擎把事件编排成跨端动作，小爱同学把自然语言翻译成触发，QoS 与离线消息保证弱网下也不丢关键指令，本地联动保证断网可用。这一章解决的是「消息怎么流、联动怎么编排」——它的工程难点不在「发一条消息」，而在「十亿设备各自发、各自收，还不丢不炸不乱」。下一章则深入「设备状态与家庭场景怎么被建模」：消息要流动，首先得有一套统一的「设备词汇表」让所有端都说得懂。

| 维度 | 工业/通用 IoT 思路 | 米家/MiOT 消费级思路 |
|------|----------------|------------------|
| 事件处理 | SCADA 脚本写死 | 事件总线 + 规则引擎，用户自助编排 |
| 可靠性 | 统一高可靠 | QoS 分级：可丢 / 至少一次 / 恰好一次 |
| 离线 | 专线保连 | 设备影子 + 离线队列，上线补发 |
| 入口 | 专业 HMI | 小爱自然语言 → 物模型字段 |
| 跨端 | 点对点硬编码 | 一处触发、多处响应、本地兜底 |

一句话收尾：设备只管发事件，规则引擎把事件编排成跨端动作，小爱把自然语言翻译成触发，QoS 与离线消息保证弱网下不丢关键指令——消费级 IoT 的「智能感」，本质是「十亿设备各自发、各自收，还不丢不炸不乱」。
